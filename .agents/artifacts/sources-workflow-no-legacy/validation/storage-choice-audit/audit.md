# Storage Choice Audit Before TDD Revision

Date: 2026-11-24. Source: `e8e32ec11983d06a91b582c820e6f097360a35f9`. The user requested an audit before choosing between existing retained-text storage and continued Convex Agent message storage. No option is accepted; the TDD remains unchanged. [Commands and provenance](request.json), [probe source](storage-choice-audit.test.ts), [measurements](measurements.json), [probe log](probes.log), and [selected regression log](existing-regressions.log) accompany this report. All new probes use real Convex modules and transaction limits, without internal mocks. Their generated text tests capacity; it is not a production workload or a comparative latency/billing benchmark.

## Existing retained text has a usable staged path, not uniform capacity behavior

`retainedText.ts:201` stages immutable fragments using a server-selected key, ordered index, byte/character totals, fragment hashes and a rolling full-content hash. Repeating an already staged identical fragment reuses it; changed content or identity is refused. Publication checks completion metadata through `completeRetainedText`, without rereading the body. `retainedTextRange:439` fetches and verifies only intersecting fragments. Its offsets are UTF-16 units; callers still own Unicode-safe public page boundaries. It scans the in-memory fragment-end manifest, so it avoids unrelated database body reads but does not provide constant-time index lookup.

This is already an integrated mechanism: `piStorage.ts:116` stages large commits through separate calls to `piStore.stageCommit` and publishes the complete reference through `publishCommit`. The mutation checks writer identity, epoch, generation, lease and mission/dossier authority; staging charges persisted bytes once under the Pi session's existing capacity. These are caller-owned controls, not automatic authorization in the generic text primitive. A new analyst-facing reader must authenticate the dossier and bind the text reference to an authorized delivery; possession of a retained-text ID is insufficient. A conversation writer must bind preparation to invocation, turn, instruction version and final publication identity.

The new real-handler probe stages 18,874,369 bytes across 308 fragments. Incomplete publication is refused, repeating the first fragment does not charge it twice, publication/republication returns the same sequence, and a ten-character suffix reads two documents totaling 35,971 logical bytes. Two publication attempts together read 59,671 logical bytes, rather than the body. Capacity-aware deletion removes the text and all its fragments in eight transactions, with a largest measured read of 5,441,625 bytes. This proves these storage boundaries at the chosen size; it does not prove Workbench end-to-end finalization, native model usefulness, deployed latency or arbitrary size support.

## Three existing convenience paths still require a whole-body transaction

`retainCompleteText:181` calls every stage in one mutation. `readRetainedText:411` reassembles every fragment in one query. `sealRetainedText:107` rereads all packed fragments to build its final manifest despite incremental append/hash checkpoints. All three fail with a transaction-capacity error at the tested 18,874,369-byte body. The stream-sealing failure rolls back and leaves the stream unsealed. This is expected diagnostic evidence, not a newly changed contract.

The single-transaction writer/readers are currently used by invocation-response and mission-result retention/recovery (`journal.ts:494,522,546`, `missionData.ts:188,209`). A conversation-body change alone cannot establish that the complete finalization path is capacity-safe. Published text may also differ from raw response JSON after domain processing. A raw response blob or internal Pi commit is not automatically the final analyst-visible text; reusing its reference without validating that identity would be wrong.

The full fragment-hash manifest accompanies every immutable stage; its end offsets grow on the same document. Whole manifests are compared/read/written repeatedly, producing increasing metadata work as fragment count grows. The sampled staged transactions remained small at 308 fragments, but this is not an unlimited store: the manifest itself must fit actual document/array limits. Cleanup validates the owner key and bounds its fragment work using remaining transaction capacity. It does not discover abandoned staged records, decide retention policy, or ensure every dossier purge caller reaches it. Existing Pi session purge deletes commits without their retained text, as recorded in the parent research; integrating a new body must specify cleanup of both published and abandoned preparations.

## Convex Agent is viable and duplication is configurable

The current application adapter splits a logical response into component messages, records their IDs and reassembles them. Installed Convex Agent 0.7.9 offers paginated thread reads and paginated whole-thread deletion (`src/component/threads.ts:136`), as well as message updating. These are useful maintained primitives, but the thread's records are fragments rather than application delivery boundaries. The application still owns exact logical-message membership, stable publication, resumable staging and idempotency after acknowledgement loss. A repeated unanchored `addMessages` call in the probe produces distinct message IDs; this is normal API behavior, not a component defect.

`addMessages` supports `hideFromUserIdSearch`, which omits the extracted `text` and user-search association while retaining the original message. The current high-level `saveMessage` helper does not forward this flag, but the installed component mutation exposes it. Both variants were executed: a 122,880-byte message is read intact with and without the flag. The default document read costs 246,006 logical bytes; the hidden-search variant costs 123,119. Therefore duplicated text is not an unavoidable reason to reject Convex Agent. Using this option gives up its user text/vector-search participation; the application's current component call sites use neither feature. This does not constitute a same-workload benchmark against retained-text storage.

Both native retrieval APIs inspected return complete component messages, not character ranges inside them. Reading selected small fragments is still possible; the application must adapt logical delivery metadata/continuation and track sizes/offsets where needed. Thread membership remains checked. If immutable integrity equivalent to retained text is required, the application must enforce or verify it rather than assuming a component message cannot be updated. No package patch or dependency change is intrinsically required for this option.

## Trade-offs and recommendation

| Direction | Benefits | Costs and constraints |
| --- | --- | --- |
| Extend existing retained-text storage | Already shared with Pi; immutable fragment identity, idempotent staging, full-content hash verification, range reads and bounded deletion have real consumers. Avoids constructing equivalent fragment mechanics around another representation. | Requires explicit conversation ownership and a publication/recovery integration. Some callers still hydrate everything. Adds a second historical body representation while old Agent records remain readable. The shared manifest and cleanup assumptions need capacity coverage because changes affect Pi and journal consumers too. |
| Keep Convex Agent bodies | Preserves existing storage references and dependency-owned message/thread operations; native pagination and deletion already exist. Search duplication can be disabled through the component API. | Still requires separate staging transactions, logical-fragment continuation, atomic publication, acknowledgement-loss idempotency and metadata for capacity-aware reads. Existing thread records do not supply the application's immutable delivery contract. More application mechanics overlap with those already implemented for retained text. |

The audit supports extending the staged immutable retained-text path, with a narrower recommendation than “reuse the existing storage”: reuse `stageRetainedText`, metadata completion and bounded range access, following the existing Pi staging pattern. Do not substitute `retainCompleteText` for the current writer or use full reads during publication. The advantage is localizing already implemented mechanics, not proven lower total cost or a missing capability in Convex Agent. Keeping Convex Agent remains technically feasible and may be preferred if preserving one physical message format outweighs the additional application-owned fragment protocol.

In both options, final visibility must remain an atomic application decision after authority/freshness checks; incomplete preparations are invisible, replay cannot publish twice, and cancellation or steering must fence stale adoption. Workbench history and the agent's historical consultation need bounded body access. These are design obligations still to approve, not delivered behavior.

## Checks and limits

Four new probes passed, including expected failure assertions for whole-body paths. Seven selected existing regressions passed: immutable staging and writer fencing, false overall-hash rejection, fragmented-request publication, confirmed observable reply retention, Unicode streaming and acknowledgement conflicts, revoked/stale Pi writers, and Pi reopening after lost acknowledgement. Fifty-five tests were excluded by the name filter, not newly skipped. No production code, permanent tests, dependency, backend or TDD was changed. No full suite, build, browser, live provider or deployment ran. Pure storage capacity is established only through the installed Convex test harness. Old-conversation range compatibility and the new conversation publication path do not yet exist and remain unverified.
