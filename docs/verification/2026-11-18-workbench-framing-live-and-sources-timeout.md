### H20 refusal and recovery

Both actual writes use `kind: open` and an `activityExcerpt` copied from the analyst's sentence. The proposed scope paraphrases that sentence. [The writer](../../convex/domain/framingProvenance.ts) requires the excerpt to occur verbatim in both the original message and `content.scope`; both writes fail the scope substring check before examining any conditional hypothesis. The [instruction and refusal feedback](../../convex/domain/workbenchAgent.ts) require an exact analyst activity phrase but do not identify the missing occurrence in the proposed scope. The returned error is the generic `framing_event_basis_invalid`.

After consulting the retained refusal, the model attributes it to speculative hypotheses and rewrites those hypotheses. The actual invalid scope/excerpt relationship remains unchanged. Repetition containment then stops the mission. This demonstrates an invalid model write combined with an insufficiently informative tool contract and recovery diagnostic. It does not justify weakening provenance checks or increasing the repetition threshold.

The unavailable-retrieval case independently reaches the same boundary. It first uses the exact analyst fragment “insurers bypass CCC during estimate review,” then changes it to the full analyst question after the refusal. Both are absent from its paraphrased scope. The agent correctly recognizes the lack of public evidence and attempts to preserve the activity, but never saves the provisional program or publishes the planned clarification. This repeated causal pattern is stronger evidence than the generic terminal `repetition_stop` label alone.

The undated case has a different failure. It uses conversation consultation and one search, acknowledges the undated illustrative lead, and publishes three reasonable research questions and a clarification. It does not read the publication or attempt to persist the program. Native completion therefore passes while the caller-visible workflow remains incomplete. The publication-date write guard was not exercised by this run. Its fallback promise to choose the most recent dated company disclosure after Start is not the agreed handling of unresolved analyst intent.

The retained protocol lacks `manifest.costAccountingPolicy`; [the relay](../../scripts/evaluations/workbench-browser/relay.mjs) therefore keeps cumulative maximum reservations instead of releasing settled reservations under `known_final_v1`. Its final summary contains 12 actual dispatches, USD2.8311552 reserved and budgeted, but USD0.0041232487 in reported model charges. Another full reservation exceeds the campaign's remaining USD2.991486937 allowance.

The application records the refused attempt with a USD0.2359296 reservation and no final provider charge. The subsequent continuation conservatively subtracts the application's entire reconciled amount; this report does not relabel that reservation as an invoiced provider charge. The interruption prevents assessing the final reply. It does not negate the saved program or the observed successful correction of missing `target.kind` fields. A future correction belongs to the existing protocol/accounting owners, not a larger evaluation budget.

## Sources: the interruption has two distinct causes

The previous Sources operation was submitted at 17:46:34.908 UTC. At 17:51:35.571, 300.663 seconds later, the Pi worker reported `execution_interrupted`; the dossier paused and advanced from generation 1 to 2. Its lease still had approximately 82 seconds. At 17:56:26.623, the already-running child control recorded `request_timeout` after 589.951 seconds. At the original research deadline, 17:57:41.699, the operation still lacked a result and became `operation_outcome_unknown`.

### Reproduced loss of the waiting dispatcher

A loopback probe executed `syscallAction` from the actual Convex Node executor bundle, outside the running service, with the same Node 26.12.1 and Undici 8.12.2. An immediate response succeeded. Holding response headers produced `UND_ERR_HEADERS_TIMEOUT` after 300.942 seconds, with one attempt and the Convex abort signal still active. A separate native-fetch control reproduced the same timeout. No provider or backend mutation was involved.

The deployed backend is identified by commit `80befbc1152f13077236bfc09284d887c478dfa5`. Its [action callback endpoint](https://github.com/get-convex/convex-backend/blob/80befbc1152f13077236bfc09284d887c478dfa5/crates/local_backend/src/node_action_callbacks.rs#L314-L343) waits for the action before sending headers. An [action-to-action caller](https://github.com/get-convex/convex-backend/blob/80befbc1152f13077236bfc09284d887c478dfa5/crates/common/src/types/functions.rs#L290-L302) does not keep the nested action running when that HTTP request disappears. The [V8 execution loop](https://github.com/get-convex/convex-backend/blob/80befbc1152f13077236bfc09284d887c478dfa5/crates/isolate/src/environment/action/mod.rs#L1182-L1190) handles cancellation outside JavaScript. Consequently, the dispatcher cannot execute either its JavaScript catch or `recordResult` after its parent disconnects. The separate Node child keeps running and can still settle its provider receipt.

This explains why the receipt exists but the operation remained running. A normal JavaScript dispatch exception would have recorded an incident and immediately marked the uncertain effect through `settleDispatchFailure`; those records are absent until deadline expiry. The original socket sub-code was replaced by `execution_interrupted`, so the historical code is not directly retained. The matching timing, actual-runtime reproduction and backend cancellation path strongly establish the mechanism.

Changing the HTTP timeout alone would not make this incident complete: the parent worker started at approximately 17:44:45.690 and would reach its own physical action limit about 101 seconds before the child returned. The existing [operation waiting state](../../convex/execution/operations.ts) and [Pi wait task](../../convex/integrations/piMission.ts) already support releasing the worker and resuming after a retained result. A bounded correction should use that mechanism for long-running documentary controls, preserving the same request identity, atomic scheduling, generation checks, settlement and idempotency. No second execution engine or arbitrary timeout increase is required.

### Unresolved excessive provider generation

Wafer reports 45,867 completion tokens, including 2,243 reasoning tokens, over 589.336 seconds, followed by cancellation. The child's application generation deadline is the 600-second Node action ceiling minus ten seconds reserved for settlement. Its non-streamed structured call retained HTTP200 and the generation ID but no assistant text before interruption.

The adjacent successful control used the same route, system instructions, reasoning, temperature and output capacity, with five contributions instead of three, and completed in 12.005 seconds with 1,414 output tokens. Both actual schemas validate with the installed AJV, including a small valid witness for the failed schema. An unsatisfiable schema and exhausted input/context capacity are not supported explanations. The missing generated content prevents distinguishing repetition, excessive JSON text or a provider/model interaction. The excessive generation remains unresolved; fixing durable waiting would preserve the outcome but would not prove that generation anomaly corrected.
