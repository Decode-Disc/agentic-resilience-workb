## CI storage-emulator correction

Candidate `a44f6c60` passed nine CI jobs; its quality job passed 3,458 of 3,459 application tests. The SEC concurrent-upload test returned one failed action instead of two successful actions sharing the winning version. Its original assertion did not include the returned failure reason. The same 21-test SEC suite passed in isolation, so this was not treated as a consistently reproduced application failure.

A deterministic storage-boundary reproduction demonstrated a transaction-ownership defect in the installed `convex-test` 0.0.62: while one upload awaits its blob hash, another action can see the global transaction as active and reuse it. If that transaction commits before the second blob read finishes, the second insert throws `Write outside of transaction`. The application's artifact persistence catches that exception and returns `failed`, providing a concrete failure route consistent with the CI outcome; the original job's exact exception remains unrecorded. The regression controls only asynchronous Blob reads and executes real SDK storage, persistence and transaction boundaries.

The [pinned SDK patch](../../patches/convex-test@0.0.62.patch) uses the caller's existing transaction lock to decide whether storage needs its own transaction. This also covers HTTP actions, which an action-type-only condition would miss. The package version and integrity were verified against the official npm registry, and the patch was applied through pnpm under Socket Firewall without changing the package version. Both concurrent entry points now pass, and deletion within an aborted mutation preserves the stored body. The SEC assertions still require success and now expose the complete returned outcome on failure. All 68 tests across these tooling, SEC, web/PDF, artifact-cleanup and inspected-material suites passed; exact-revision CI remains the final aggregate gate.
